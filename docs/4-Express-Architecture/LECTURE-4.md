# Тема 4. Backend на Express: слои, ответственность, валидация

> **Организационное примечание.** По расписанию лекция и первый семинар проходят в один день, но их порядок может отличаться. Материал написан так, чтобы быть самодостаточным независимо от порядка.

## Зачем это нужно

У тебя есть работающий сервер — и весь он лежит в одном файле `server/index.ts`. Пока эндпоинтов три, это даже удобно: всё перед глазами, ничего не нужно искать.

Дальше файл будет только расти. К каждому эндпоинту добавится работа с базой данных, потом проверка прав доступа, потом тесты. Если ничего не менять, к концу курса `index.ts` перевалит за несколько сотен строк, и чтобы поправить в нём одну проверку, придётся вычитывать весь файл целиком.

Эта тема — про то, как разложить сервер по местам заранее, пока он ещё маленький и разложить его легко. Заодно выяснится, что «разложить по папкам» — не про красоту и не про порядок ради порядка: у каждого слоя есть работа, которую он делает, и работа, которую он не делает никогда.

**Если ты разберёшься с материалом этой темы, то:**

- Поймёшь, зачем код делят на слои, и научишься отвечать на вопрос «а куда положить вот эту новую строчку»;
- Разложишь свой сервер на роуты, контроллеры и сервисы — и начнёшь узнавать это же устройство в чужих проектах, потому что оно стандартное;
- Научишься проверять входные данные один раз в одном месте, а не в каждом обработчике заново;
- Подготовишь сервер к базе данных так, что при переезде менять придётся ровно один файл.

**Тебе для этой темы нужно помнить:**

- С прошлой темы: формулу `app.метод(путь, обработчик)`, что такое middleware и `app.use()`, порядок регистрации, статус-коды 200/201/400/404/500;
- Из клиента: как файлы обмениваются кодом через `export` и `import` — ты делал это с каждым компонентом;
- Что свои файлы на сервере импортируются **с расширением `.ts`** — вот сейчас это и пригодится.

## Необходимо знать для дальнейшего: три слова про устройство кода

### Модуль

> [!NOTE] Определение
> **Модуль** — отдельный файл с кодом, который сам решает, что из него видно снаружи: помеченное словом `export` могут забрать другие файлы, всё остальное остаётся внутри файла и недоступно никому.

Если сказать проще: модуль — это коробка с ручкой сбоку. Внутри может лежать что угодно, но наружу торчит только то, за что ты разрешил браться. На клиенте ты этим пользовался с первого дня: `export function BoardCard(...)` в одном файле, `import { BoardCard } from ...` — в другом.

> [!WARNING] Предостережение
> На сервере свои файлы импортируются **с расширением `.ts`**: `import { createCard } from "./cards.service.ts"`. Не `"./cards.service"` и не `"./cards.service.js"`. Пока сервер помещался в один файл, импортировать было нечего и правило не всплывало; сегодня файлов станет много, и забытое расширение будет самой частой ошибкой дня. Ошибка при этом выглядит так: `Cannot find module ... imported from ...`.

### Ответственность

> [!NOTE] Определение
> **Ответственность** модуля — тот единственный вопрос, на который он отвечает. У хорошо устроенного модуля такой вопрос ровно один.

Если сказать проще: попробуй одним предложением сказать, за что отвечает файл. Если в предложении появляются «и» — «отвечает за адреса, **и** за проверку данных, **и** за создание карточек» — файл делает слишком много, и это первый признак, что его пора делить.

### Слой

> [!NOTE] Определение
> **Слой** — модули, которые играют в программе одну и ту же роль: отвечают на вопрос одного и того же рода, каждый про свою часть предметной области. Слои выстроены в цепочку, и каждый обращается только к следующему.

Если сказать проще: слой — это этаж, а модули на нём — кабинеты. В соседних кабинетах занимаются разными предметами — в одном ведают карточками, в другом пользователями, — но работа у всех на этаже одного рода, и с соседним этажом общаются через лестницу, а не через окно.

> [!IMPORTANT] Важно
> Модули одного слоя не сливают в один файл именно потому, что **ответственность у них разная**: `cards.service.ts` отвечает за то, что значат операции с карточками, `users.service.ts` — за то, что значат операции с пользователями. Одинаков у них не ответ, а вопрос: «что эта операция значит по сути». Роль общая — предмет разный.
>
> Пока предмет в проекте один, на этаже стоит один кабинет: сегодня в каждом слое у тебя будет ровно по одному файлу, и папки будут выглядеть избыточными. Как только у доски появятся пользователи — а без них не обойтись, карточка должна знать своего владельца, — рядом встанут `users.service.ts` и `users.controller.ts`. Вот тогда папки и окупятся.

## Один файл на всё: чем это плохо

Вот что лежит в `server/index.ts` сейчас, если убрать тела функций и оставить только суть:

```typescript
const cards: Card[] = [
  /* три карточки */
]; // данные

app.use(express.json()); // разбор тела
app.use((req, res, next) => {
  /* логгер */
}); // логирование

app.get("/cards", (req, res) => {
  /* отдать массив */
});

app.post("/cards", (req, res) => {
  const { title } = req.body;
  if (!title || !title.trim()) {
    /* 400 */
  } // проверка данных
  const newCard = {
    /* собрать карточку */
  }; // логика создания
  cards.push(newCard); // работа с данными
  res.status(201).json(newCard); // формирование ответа
});

app.delete("/cards/:id", (req, res) => {
  /* найти, удалить, ответить */
});

app.use((req, res) => {
  /* 404 */
});
app.use((err, req, res, next) => {
  /* 500 */
});
```

Файл небольшой, и на первый взгляд с ним всё в порядке. Проблемы видно, если задать те самые вопросы из определений выше.

**За что отвечает этот файл?**

- За запуск приложения (вызов `.listen()`);
- За список обрабатываемых эндпоинтов;
- За проверку входных данных в отдельном эндпоинте;
- За то, что вообще значит «создать карточку»;
- За то, где эти карточки хранятся.

**Пять ответственностей** в одном файле.

Отсюда три вполне практических неудобства:

- **Чтобы поправить одно, нужно читать всё.** Проверка `title` живёт внутри обработчика `POST`, вперемешку с роутингом и формированием ответа. Чтобы её найти, надо прочитать обработчик целиком.
- **Логику нельзя переиспользовать.** Сегодня карточка создаётся только по запросу `POST /cards`. Завтра её понадобится создавать ещё где-то — например, копированием другой карточки. Логика создания заперта внутри обработчика, и единственный способ её достать — скопировать.
- **Ничего нельзя проверить, не запуская сервер.** Чтобы убедиться, что пустой `title` не проходит, надо поднять сервер и послать настоящий запрос. Когда дойдёт до автотестов, это станет прямой проблемой: тест вызывает функцию и сверяет результат, а «подними сервер и потыкай» автоматизировать нечем.

Заметь: сервер при этом **работает правильно**. Речь не про баги, а про то, что с таким кодом тяжело жить дальше. Именно это и называется архитектурой — не «работает или нет», а «во что обойдётся следующее изменение».

## Три слоя: роут, контроллер, сервис

Стандартное решение — разложить обработку запроса на три слоя. Каждый отвечает ровно на один вопрос.

> [!NOTE] Определение
> **Роут** (слой маршрутизации) отвечает на вопрос **«какие адреса существуют»**: перечисляет эндпоинты и говорит, какая функция обслуживает каждый. Больше ничего не делает.
>
> **Контроллер** отвечает на вопрос **«как перевести HTTP-запрос в задачу и обратно»**: достаёт из `req` нужные данные, зовёт того, кто сделает работу, и превращает результат в `res` — статус-код и тело ответа.
>
> **Сервис** отвечает на вопрос **«что вообще значит эта операция»**: что такое «создать карточку», «удалить карточку». Про HTTP не знает вовсе.

Если сказать проще, на примере «создать карточку»:

- роут: «`POST` на `/cards` обслуживает вот эта функция»;
- контроллер: «в теле запроса лежит `title` — беру его, прошу создать карточку, отвечаю кодом 201 и получившейся карточкой»;
- сервис: «создать карточку — значит придумать ей `id`, проставить `isDone: false` и положить в хранилище».

| Слой       | Отвечает на вопрос                      | Знает про `req` и `res`? | Знает про статус-коды? |
| ---------- | --------------------------------------- | ------------------------ | ---------------------- |
| Роут       | какие адреса есть                       | нет                      | нет                    |
| Контроллер | как перевести запрос в задачу и обратно | да                       | да                     |
| Сервис     | что значит операция по сути             | **нет**                  | **нет**                |

Главное в этой таблице — последняя строка.

> [!IMPORTANT] Важно
> **Чем глубже слой, тем меньше он знает про HTTP.** Сервис не знает, что такое `res`, не знает про код 404 и вообще не подозревает, что его вызвали из-за какого-то запроса. Это не формальность: ровно поэтому ту же функцию сервиса можно будет вызвать откуда угодно — из другого сервиса, из скрипта, из автотеста, — и она сработает, потому что ей ничего не нужно, кроме своих аргументов.

Правило, по которому решается «куда положить новую строчку», следует из той же таблицы: **строчка живёт в том слое, чьи знания ей нужны**. Понадобился `res.status(...)` — это контроллер. Понадобилось узнать, есть ли уже такая карточка, — это сервис. Не понадобилось ни то ни другое, а нужно просто назвать адрес — это роут.

## Роутер: как роуты переезжают в свой файл

Роуты нужно вынести из `index.ts` — но `app` живёт именно там, а `app.get(...)` без `app` не напишешь. Для этого у Express есть отдельная вещь.

> [!NOTE] Определение
> **Роутер** (`Router`) — набор правил роутинга, живущий отдельно от приложения. Правила в нём описываются той же формулой, что и раньше, а потом весь набор целиком подключается к приложению одной строкой.

Если сказать проще: роутер — это мини-приложение, у которого есть свои роуты, но нет своего порта. Его пишут в отдельном файле, а потом приносят и вставляют в настоящее приложение.

```typescript
// routes/cards.routes.ts
import { Router } from "express";

export const cardsRouter = Router();

cardsRouter.get("/" /* обработчик */);
cardsRouter.post("/" /* обработчик */);
cardsRouter.delete("/:id" /* обработчик */);
```

А в `index.ts` весь набор подключается той самой формой `app.use()` с путём — она до сих пор не пригождалась, потому что роуты лежали в одном файле с приложением:

```typescript
app.use("/cards", cardsRouter);
```

Читается: «всё, что начинается с `/cards`, обслуживает `cardsRouter`».

> [!IMPORTANT] Важно
> Пути внутри роутера пишутся **относительно префикса**, а не от начала. Префикс `/cards` уже назван в `app.use()`, и повторять его внутри не нужно:
>
> | В `index.ts`                     | В роутере                    | Итоговый эндпоинт           |
> | -------------------------------- | ---------------------------- | --------------------------- |
> | `app.use("/cards", cardsRouter)` | `cardsRouter.get("/")`       | `GET /cards`                |
> | `app.use("/cards", cardsRouter)` | `cardsRouter.delete("/:id")` | `DELETE /cards/1`           |
> | `app.use("/cards", cardsRouter)` | `cardsRouter.get("/cards")`  | `GET /cards/cards` ← ошибка |
>
> Последняя строка — самая частая ошибка при переезде на роутер: префикс случайно указывают дважды, и эндпоинт уезжает по несуществующему адресу.

### Ловушка порядка внутри роутера

Ты уже знаешь, что Express перебирает правила строго сверху вниз и ничего не сортирует. Теперь, когда появились пути с параметром, из этого вырастает ловушка.

Допустим, к существующему `GET /cards/:id` понадобилось добавить `GET /cards/done` — все выполненные карточки:

```typescript
cardsRouter.get("/:id" /* отдать одну карточку по id */);
cardsRouter.get("/done" /* отдать выполненные */); // сюда очередь не дойдёт никогда
```

Запрос `GET /cards/done` подходит уже под первую строку: `:id` — это «любое слово на этом месте», и слово `done` под него честно подходит. Сервер будет искать карточку с `id` равным `"done"`, не найдёт и ответит 404, хотя второе правило описывает этот путь точнее.

> [!WARNING] Предостережение
> Точные пути регистрируются **выше** параметрических — всегда. `"/done"` перед `"/:id"`, и всё работает. Никакой настройки для этого нет и быть не может: Express не сортирует правила, он идёт по списку в том порядке, в каком ты их написал.

## Как выглядит разложенный сервер

Структура папок:

```
server/
  index.ts                       # запуск: middleware, подключение роутера, обработка ошибок
  routes/
    cards.routes.ts              # какие адреса есть у карточек
  controllers/
    cards.controller.ts          # перевод между HTTP и сервисом
  services/
    cards.service.ts             # что значит создать/удалить карточку + хранилище
  middleware/
    validateNewCard.ts           # проверка входных данных
  types/
    card.ts                      # тип Card
```

Дальше — по файлам, в том порядке, в каком по ним проходит запрос.

### `index.ts` — только сборка приложения

```typescript
import express from "express";
import { cardsRouter } from "./routes/cards.routes.ts";

const app = express();

app.use(express.json());
app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`);
  next();
});

app.use("/cards", cardsRouter);

app.use((req, res) => {
  res.status(404).json({ error: `Такого пути нет: ${req.method} ${req.url}` });
});

app.use((err: Error, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: "Что-то сломалось на сервере" });
});

app.listen(3001, () => {
  console.log("Сервер запущен: http://localhost:3001");
});
```

Файл стал короче, чем был, и — главное — его ответственность теперь одна: собрать приложение из частей и запустить. Ни одной строчки про то, что такое карточка, здесь больше нет.

Порядок регистрации при этом остался прежним и по той же причине, что и раньше: общие middleware — сверху, роутер — в середине, обработчики 404 и ошибок — в самом низу.

### `routes/cards.routes.ts` — список адресов

```typescript
import { Router } from "express";
import * as cardsController from "../controllers/cards.controller.ts";
import { validateNewCard } from "../middleware/validateNewCard.ts";

export const cardsRouter = Router();

cardsRouter.get("/", cardsController.getAll);
cardsRouter.post("/", validateNewCard, cardsController.create);
cardsRouter.delete("/:id", cardsController.remove);
```

Три строки — три эндпоинта, и по ним сразу видно всё устройство API. Это и есть польза слоя: чтобы узнать, какие адреса есть у сервера, достаточно открыть один файл на десять строк.

> [!TIP] Совет
> `import * as cardsController` читается как «возьми из модуля всё, что он экспортирует, и сложи в объект `cardsController`». Так в коде видно, откуда функция: `cardsController.create` — из контроллера, а не откуда-то отсюда. Пригождается именно здесь, потому что функция контроллера и функция сервиса вполне могут называться одинаково — `create` и там, и там.

### `controllers/cards.controller.ts` — перевод HTTP ↔ задача

```typescript
import type { Request, Response } from "express";
import * as cardsService from "../services/cards.service.ts";

export async function getAll(req: Request, res: Response) {
  const cards = await cardsService.getAll();
  res.json(cards);
}

export async function create(req: Request, res: Response) {
  const { title } = req.body;
  const card = await cardsService.create(title.trim());
  res.status(201).json(card);
}

export async function remove(req: Request, res: Response) {
  const isDeleted = await cardsService.remove(req.params.id);

  if (!isDeleted) {
    res.status(404).json({ error: "Карточка не найдена" });
    return;
  }

  res.status(204).end();
}
```

Каждая функция здесь делает ровно три вещи: достаёт нужное из `req`, зовёт сервис, формирует `res`. Никакой работы с карточками — ни поиска, ни создания `id` — в контроллере нет.

> [!IMPORTANT] Важно
> Обрати внимание на первую строку: `import type { Request, Response } from "express"`. Раньше типы `req` и `res` писать не приходилось — пока обработчик лежал прямо внутри `app.get(...)`, TypeScript видел, куда эта функция передаётся, и выводил типы сам. Вынесенная в отдельный файл функция такого контекста лишена: она просто функция, и что ей передадут — неизвестно. Поэтому типы приходится назвать явно, и берутся они из `@types/express` — пакета, который ты поставил вместе с самим Express.

О статус-коде `204` — он в курсе новый: означает «успешно, и отвечать нечем». Для удаления подходит идеально: возвращать нечего, карточки больше нет. Пара `res.status(204).end()` вместо `res.json(...)` — как раз про это: `end()` завершает ответ без тела. Если на семинаре, когда ты писал удаление, выбор пал на другой код — оставь свой: здесь важен не сам номер, а то, что решение об ответе принимает контроллер.

### `services/cards.service.ts` — суть операций

```typescript
import type { Card } from "../types/card.ts";

const cards: Card[] = [
  {
    id: "1",
    title: "Спроектировать структуру доски",
    isDone: true,
    isUrgent: false,
  },
  {
    id: "2",
    title: "Подключить доску к серверу",
    isDone: false,
    isUrgent: true,
  },
  {
    id: "3",
    title: "Добавить фильтр выполненных карточек",
    isDone: false,
    isUrgent: false,
  },
];

export async function getAll(): Promise<Card[]> {
  return cards;
}

export async function create(title: string): Promise<Card> {
  const newCard: Card = {
    id: String(Date.now()),
    title,
    isDone: false,
    isUrgent: false,
  };
  cards.push(newCard);
  return newCard;
}

export async function remove(id: string): Promise<boolean> {
  const index = cards.findIndex((card) => card.id === id);

  if (index === -1) {
    return false;
  }

  cards.splice(index, 1);
  return true;
}
```

Перечитай этот файл и убедись: в нём нет ни одного слова про HTTP. Ни `req`, ни `res`, ни статус-кодов, ни даже упоминания, что где-то есть сервер. Это просто функции работы с карточками — их можно вызвать откуда угодно.

### Путь запроса целиком

```
POST /cards  { "title": "Написать лекцию" }
  │
  ├─ index.ts             express.json() разобрал тело, логгер записал строку
  ├─ index.ts             путь начинается с /cards → передать в cardsRouter
  ├─ cards.routes.ts      POST на "/" → сначала validateNewCard, потом контроллер
  ├─ validateNewCard.ts   title непустой → next()
  ├─ cards.controller.ts  достал title, позвал сервис
  ├─ cards.service.ts     придумал id, положил карточку в массив, вернул её
  └─ cards.controller.ts  ответил 201 и карточкой
```

Файлов стало шесть вместо одного, и это честная цена: чтобы понять, как обрабатывается запрос целиком, теперь нужно открыть несколько файлов вместо одного. Взамен каждый из них читается за десять секунд и правится, не задевая остальные. Ради трёх эндпоинтов такой размен не окупился бы — ради двух десятков, до которых доска дорастёт вместе с пользователями и правами доступа, окупается многократно.

## Валидация входных данных

> [!NOTE] Определение
> **Валидация** — проверка входных данных на пригодность до того, как программа начнёт с ними работать: есть ли обязательное поле, того ли оно типа, не пустое ли.

До сих пор проверка пустого `title` жила прямо внутри обработчика `POST /cards`. Теперь надо решить, в какой слой она переезжает, — и ни один из трёх не подходит идеально:

- **не сервис**: он не знает про HTTP, а ответить на плохие данные нужно кодом 400 — это знание контроллера;
- **не контроллер**: тогда в каждом контроллере, принимающем данные, будет своя копия проверок, и они разъедутся.

Поэтому валидацию выносят в **отдельную промежуточную функцию** — то самое middleware, только своё и с конкретной задачей:

```typescript
// middleware/validateNewCard.ts
import type { Request, Response, NextFunction } from "express";

export function validateNewCard(
  req: Request,
  res: Response,
  next: NextFunction,
) {
  const { title } = req.body;

  if (typeof title !== "string" || !title.trim()) {
    res.status(400).json({ error: "title обязателен и не может быть пустым" });
    return;
  }

  next();
}
```

Ровно та же конструкция, что и у логгера, который ты писал раньше: три параметра, и либо `next()`, либо ответ. Здесь она наконец делает что-то полезное — не пускает дальше запрос с негодными данными.

### Формула роута расширяется

Подключается такая проверка прямо в строке роута:

```typescript
cardsRouter.post("/", validateNewCard, cardsController.create);
```

Знакомая тебе формула `app.метод(путь, обработчик)` оказывается короткой версией полной:

```
app.метод(путь, промежуточная_функция, ..., обработчик)
```

Между путём и обработчиком можно поставить сколько угодно промежуточных функций, и они выполнятся по очереди слева направо. Каждая решает всё то же самое: пропустить дальше (`next()`) или ответить самой и на этом закончить.

> [!IMPORTANT] Важно
> Отсюда важное следствие для контроллера. Раз `validateNewCard` стоит **до** `cardsController.create`, до контроллера доедут только запросы с годным `title`. Поэтому в контроллере проверка не повторяется — там сразу `title.trim()`, без всяких «а вдруг пусто». Проверка сделана один раз в одном месте, и в этом весь смысл затеи.

> [!TIP] Совет
> Сейчас проверки написаны руками, и уже на трёх-четырёх полях это станет утомительным, а на десяти — источником ошибок: какое-нибудь поле обязательно забудут проверить. Поэтому ручные `if` со временем заменяют библиотекой, которая описывает форму данных одной схемой и проверяет по ней сама. Самая распространённая такая библиотека называется **Zod**; в обязательную программу курса она не входит, но если решишь посмотреть — место не изменится: схема встанет ровно сюда же, в промежуточную функцию перед контроллером.

## Как сервису сообщить об ошибке, не зная про HTTP

Посмотри ещё раз на удаление. Сервис может не найти карточку — но ответить «404» он не может: про статус-коды знает только контроллер. Как тогда сообщить?

Решение видно в коде выше: **сервис возвращает результат, а решение о статус-коде принимает контроллер**.

```typescript
// сервис: "удалил" или "нечего было удалять"
export async function remove(id: string): Promise<boolean> {
  /* ... */
}
```

```typescript
// контроллер: превращает ответ сервиса в HTTP
const isDeleted = await cardsService.remove(req.params.id);
if (!isDeleted) {
  res.status(404).json({ error: "Карточка не найдена" });
  return;
}
res.status(204).end();
```

Так же поступают, когда нужно вернуть одну карточку: сервис отдаёт `Card` или `null`, а контроллер сам решает — `200` и карточка либо `404` и сообщение.

> [!IMPORTANT] Важно
> Граница между слоями проходит именно здесь, и её легко нарушить незаметно. Стоит один раз написать в сервисе `res.status(404)` — и сервис перестаёт быть сервисом: его больше нельзя вызвать из другого места, потому что он требует `res`. Признак нарушения простой: **если в файле сервиса встретилось слово `res` — граница уже сломана**.

### P.S. Подготовка к базе данных

Массив в памяти — временное решение: данные в нём живут ровно до перезапуска сервера. Рано или поздно карточки переедут в настоящую базу данных, и разложенный по слоям сервер к этому уже готов. Стоит понять, чем именно.

**Первое: место хранения известно ровно одному файлу.** Массив `cards` объявлен в `cards.service.ts`, и больше нигде в проекте о нём не знают: контроллер зовёт `cardsService.getAll()` и понятия не имеет, откуда та берёт данные — из массива, из файла или из базы. При переезде внутренности этих функций перепишутся на запросы в базу данных, а контроллеры, роуты и `index.ts` не изменятся ни на строчку.

**Второе: функции сервиса уже асинхронные.** Ты наверняка заметил `async` и `Promise<Card[]>` в сервисе, хотя массиву никакая асинхронность не нужна — `return cards` отработал бы мгновенно и без всякого `async`. Это сделано намеренно:

> [!NOTE] Определение
> **Асинхронная операция** — та, результат которой приходит не сразу: программа отправляет запрос и продолжает работать, а получает ответ позже. Обращение к базе данных всегда такое: база — отдельная программа, часто на другом компьютере, и ответ от неё идёт заметное время.

Ты уже писал такой код на клиенте: `await fetch("/api/cards")` в `client/src/api/cards.ts` — там `await` ждал ответа сервера. Здесь будет то же самое, только ждать будут ответа базы данных.

Будь сервис сейчас синхронным, при переезде на базу данных переписывать пришлось бы не только его, но и каждый контроллер — дописывать в них `await` и `async`. А раз тронут каждый контроллер, то и проверять после этого надо всё: не сломалось ли где-то то, что уже работало. Сделав функции асинхронными заранее, мы платим одним лишним словом сегодня — и не платим ничем потом.

## Частые ошибки новичков

- **Забыто расширение `.ts` в импорте** — `Cannot find module`. Самая частая ошибка этой темы, потому что импортов стало много;
- **Префикс пути указан дважды** — `app.use("/cards", ...)` и внутри роутера `router.get("/cards")`, в результате эндпоинт живёт по адресу `/cards/cards`;
- **Параметрический путь зарегистрирован выше точного** — `"/:id"` перед `"/done"`, и до точного очередь не доходит никогда;
- **`res` в сервисе** — граница слоёв сломана, сервис больше нельзя вызвать ниоткуда, кроме обработчика запроса;
- **Логика в контроллере** — контроллер сам ищет карточку в массиве и сам её создаёт, а сервис используется как склад для одной строчки. Признак: контроллер длиннее десяти строк;
- **Валидация продублирована** — проверка стоит и в промежуточной функции, и в контроллере; при изменении правил одну из копий забывают поправить;
- **Слои ради слоёв** — отдельная папка и файл заводятся под каждую мелочь, и чтобы прочитать одну операцию, приходится открывать шесть файлов вместо трёх. Слой оправдан тогда, когда у него есть своя ответственность, а не потому, что «так в статье написано».

## Заключение

Собери тему в одну картину:

- Разложение на слои — не про красоту, а про цену будущих изменений: сервер работал и одним файлом, но каждая следующая тема делала бы этот файл тяжелее;
- Три слоя отвечают на три разных вопроса: роут — «какие адреса есть», контроллер — «как перевести запрос в задачу и обратно», сервис — «что эта операция значит по сути»;
- Чем глубже слой, тем меньше он знает про HTTP: в сервисе не должно быть ни `res`, ни статус-кодов — именно это делает его вызываемым откуда угодно, в том числе из автотестов;
- Роутер собирает эндпоинты в отдельный файл и подключается одной строкой `app.use("/cards", cardsRouter)`; пути внутри пишутся относительно префикса, а точные пути регистрируются выше параметрических;
- Валидация живёт в промежуточной функции перед контроллером — один раз в одном месте; когда ручных проверок станет слишком много, на это же место ставят схему проверяющей библиотеки — например, Zod;
- Сервер уже подготовлен к базе данных: место хранения известно одному файлу, а функции сервиса асинхронны заранее.

Когда массив `cards` заменится настоящей базой данных, проверка того, насколько аккуратно разложены слои, окажется очень простой: если менять придётся только `cards.service.ts`, разложено правильно.
