> **Организационное примечание.** Семинар и лекция по этой теме проходят в один день, порядок может отличаться. В каждом задании указано, в каком разделе лекции ([LECTURE-5.md](LECTURE-5.md)) лежит нужный образец кода, — если семинар у тебя идёт первым, открывай лекцию прямо по ходу работы.

> [!IMPORTANT] Проверь перед началом

**Дедлайн сдачи семинара:** первое занятие Темы 7.

## Перед началом: ставим PostgreSQL

Это единственный шаг темы, где ломается не код, а окружение. Заложи на него время и не стесняйся звать преподавателя: дальше всё будет одинаково у всех, а здесь у каждого своя операционная система.

| Система     | Как поставить                                                                              |
| ----------- | ------------------------------------------------------------------------------------------- |
| Windows     | Установщик с [postgresql.org/download/windows](https://www.postgresql.org/download/windows/). **Запиши пароль**, который зададут при установке, — он понадобится через десять минут |
| macOS       | [Postgres.app](https://postgresapp.com/) — проще всего, или `brew install postgresql@17`      |
| Linux       | `sudo apt install postgresql` (Ubuntu/Debian) или аналог для своего дистрибутива              |

Проверка, что всё встало:

```bash
psql --version
```

Ответ вида `psql (PostgreSQL) 17.x` — можно идти дальше.

> [!TIP] Совет
> `команда не найдена` не означает, что база не поставилась: скорее всего, программа `psql` просто не попала в `PATH`. На Windows её можно запустить из меню «Пуск» — пункт **SQL Shell (psql)**; на macOS с Postgres.app путь добавляется в настройках самого приложения. Если возиться некогда — позови преподавателя, это чинится за минуту.

Дальше нужно завести саму базу. Имя — `kanban`:

```bash
psql -c "CREATE DATABASE kanban;"
```

> [!WARNING] Предостережение
> На Windows подключаться придётся под пользователем `postgres` — тем самым, чей пароль ты записал при установке. Тогда все команды `psql` в этом семинаре пишутся с добавкой `-U postgres`:
>
> ```bash
> psql -U postgres -c "CREATE DATABASE kanban;"
> ```
>
> На macOS и Linux пользователь по умолчанию — твой собственный, и `-U` не нужен. Запомни, какой вариант сработал у тебя: эта же добавка понадобится в скрипте `db:reset` и в строке подключения.

Проверка, что база создалась:

```bash
psql -d kanban -c "SELECT 1;"
```

Таблица с единичкой в ответ — база на месте и принимает запросы.

## Задание 1 (промежуточное). Схема, данные, подключение

**Навык:** схема в виде скрипта, разворачивание базы одной командой, пул соединений.
**Ветка:** `feature/database-setup`.

В этом задании ты ещё не трогаешь код сервера — только заводишь базу и учишь сервер до неё дозваниваться. Образцы — лекция, разделы «Схема доски», «Начальные данные: `seed.sql`», «Разворачиваем базу одной командой» и «Подключение: пул соединений».

1. Создай ветку `feature/database-setup` от `main`.
2. Заведи папку `server/db/` и положи в неё `schema.sql` — две таблицы, `users` и `cards`, по образцу из лекции.
3. Рядом положи `seed.sql`: один пользователь и те же три карточки, что сейчас лежат в массиве `cards.service.ts`. Владелец карточек ищется скалярным подзапросом по почте — как в лекции.
4. Добавь в `server/package.json` скрипт `db:reset`, который выполняет оба файла подряд. Запусти `npm run db:reset` из папки `server/`.
5. Убедись, что данные на месте: `psql -d kanban -c "SELECT * FROM cards;"` — три строки.
6. Поставь `pg` обычной зависимостью и `@types/pg` — с `--save-dev`.
7. Создай `server/.env` со строкой `DATABASE_URL=...` и `server/.env.example` — с теми же ключами, но фиктивным паролем. Добавь в скрипт `dev` флаг `--env-file=.env`.
8. Создай `server/db/pool.ts` с единственным пулом на всё приложение.
9. Проверь связь: временно допиши в `index.ts` перед `app.listen(...)` запрос к базе и вывод результата в консоль:

```typescript
const check = await pool.query("SELECT count(*) FROM cards");
console.log("Карточек в базе:", check.rows[0].count);
```

Запусти `npm run dev` — в терминале должно появиться `Карточек в базе: 3`. После проверки эти строки удали, отдельным коммитом.

**Готово, когда:**

- [ ] `npm run db:reset` отрабатывает без ошибок и **дважды подряд** — скрипт можно запускать сколько угодно раз, он всегда возвращает базу в исходное состояние;
- [ ] `psql -d kanban -c "SELECT * FROM cards;"` показывает три карточки, и у каждой заполнен `owner_id`;
- [ ] `psql -d kanban -c "SELECT * FROM users;"` показывает одного пользователя;
- [ ] при запуске сервера в терминале печатается число карточек, взятое из базы;
- [ ] файла `.env` **нет** среди изменений в панели Source Control, а `.env.example` — есть;
- [ ] в ветке отдельные коммиты: схема и данные, скрипт `db:reset`, подключение через пул, удаление проверочных строк.

> [!WARNING] Предостережение
> Порядок в `schema.sql` важен дважды. `DROP TABLE` — сначала `cards`, потом `users`, иначе внешний ключ не даст удалить родительскую таблицу. `CREATE TABLE` — наоборот, сначала `users`: ссылаться можно только на то, что уже существует. Ошибка выглядит как `relation "users" does not exist`.

> [!TIP] Совет
> Ошибка `password authentication failed` или `database "kanban" does not exist` при запуске сервера — почти всегда опечатка в `DATABASE_URL`. Собери строку из того, что уже сработало в командной строке: если у тебя работает `psql -U postgres -d kanban`, то строка будет `postgres://postgres:твой_пароль@localhost:5432/kanban`.

## Задание 2 (промежуточное). Репозиторий вместо массива

**Навык:** четвёртый слой, параметризованные запросы, перевод «строка таблицы → объект».
**Ветка:** `feature/cards-repository`.

Сначала Git: влей `feature/database-setup` в `main` своей копии, переключись на `main`, нажми «Sync Changes» и создай ветку `feature/cards-repository`.

Это **рефакторинг**: снаружи приложение обязано вести себя ровно как раньше. Те же эндпоинты, те же ответы, та же доска в браузере — меняется только то, откуда берутся данные. Образцы — лекция, разделы «Почему появился четвёртый слой», «Те же четыре слоя в коде» и «Что вернула база — что ответил сервер».

1. Создай `server/repositories/cards.repository.ts`. В нём: тип строки таблицы, функция перевода строки в `Card` и функции запросов — получить все, создать, удалить, плюс та, что меняет отметку выполнения из задания темы 4.
2. Перепиши `cards.service.ts`: массива карточек в нём больше нет, каждая функция зовёт репозиторий.
3. Разберись с владельцем карточки. Входа в приложение ещё нет, поэтому пока — временная константа в сервисе, с честным комментарием:

```typescript
// Временно, до темы 6: пока входа нет, все карточки создаёт один и тот же пользователь.
// Это id пользователя из seed.sql — после npm run db:reset он всегда равен 1.
const CURRENT_USER_ID = 1;
```

4. В контроллере преврати `id` из адреса в число и проверь, что это вообще число: не число — `400`, не доводя запрос до базы.
5. Проверь доску целиком: карточки видны, создаются, удаляются, отметка ставится и снимается.
6. А теперь главное ради чего всё затевалось: создай карточку, **перезапусти сервер** и обнови страницу. Карточка на месте.

**Готово, когда:**

- [ ] массива карточек в проекте больше нет — поиск по `server/` не находит ни одного захардкоженного `title`;
- [ ] поиск по проекту слова `SELECT` находит его **только** в файлах папки `repositories/`;
- [ ] доска работает как до рефакторинга: карточки отображаются, создаются, удаляются, отметка выполнения ставится и снимается;
- [ ] созданная карточка переживает перезапуск сервера;
- [ ] значения в запросы попадают только через `$1`, `$2`, … — внутри текста запроса нет ни одного `${`;
- [ ] `DELETE /cards/abc` отвечает `400`, а не `500` — проверь в браузере или через доску, подставив в адрес ерунду;
- [ ] удаление несуществующей карточки (`DELETE /cards/999`) отвечает `404`;
- [ ] в контроллере и сервисе нет ни одного упоминания столбцов вида `is_done` — snake_case живёт только в репозитории;
- [ ] в ветке отдельные коммиты: репозиторий, переписанный сервис, обработка `id` в контроллере.

> [!TIP] Совет
> Доска пустая, а в терминале сервера ошибок нет — почти наверняка `return result.rows` вместо `return result.rows.map(toCard)`. Фронт получил объекты с полем `is_done`, прочитал `card.isDone`, получил `undefined` — и нарисовал то, что смог. Открой инструменты разработчика браузера (`F12`), вкладку Network, посмотри на ответ сервера: если в нём `is_done` — дело в этом.

## Задание 3 (оценочное). Тикет KAN-5

Задача целиком по конвейеру: разведка, постановка (`proposal.md` и спека), `design.md` и `tasks.md`, реализация по шагам, архивация. Предмет — ровно то, ради чего была вся лекция: HTTP-запрос от фронта превращается в условие внутри SQL-запроса.

> [!IMPORTANT] Проверь перед началом
> Задание опирается на фильтр «скрыть выполненные», который ты сделал в оценочном задании темы 1: стор `useBoardFiltersStore` с полем `hideDone` и отбор карточек в `BoardColumn`. Если тема 1 не закрыта — переносить на сервер будет нечего.

Влей `feature/cards-repository` в `main` своей копии и создай ветку `feature/server-side-filter`.

> **KAN-5: Фильтр «скрыть выполненные» отсеивает карточки уже после того, как они приехали**
>
> Переключатель в шапке доски работает, но отбор делает браузер: сервер присылает все карточки до единой, а колонка часть из них просто не показывает. Пока карточек десяток, разницы не заметно. На доске из нескольких сотен по сети едет всё, а на экране остаётся половина — и чем больше доска, тем больше зря переданных данных.
>
> **Критерии приёмки:**
>
> 1. Состояние переключателя уходит на сервер параметром строки запроса;
> 2. Отбор карточек делает база — условием внутри SQL-запроса; после получения строк карточки нигде больше не отсеиваются;
> 3. Переключение фильтра приводит к новому запросу к серверу и обновлению доски;
> 4. Запрос с негодным значением параметра отклоняется кодом `400`;
> 5. Если под фильтр не подошло ничего, сервер отвечает `200` и пустым списком, а доска показывает пустую колонку — не ошибку загрузки;
> 6. Значение параметра попадает в SQL только через `$1`; склейки строк в тексте запроса нет;
> 7. Без параметра запрос уходит в базу вообще без условия — `WHERE` появляется только тогда, когда фильтр включён.

Как назвать параметр и какие значения он принимает, тикет намеренно не говорит — это решаешь ты: поведение — требованием спеки, обоснование выбора — в `design.md`. Подумай заодно, что должно происходить, если параметра нет вовсе: это тоже решение, и критерий 7 намекает, какое.

Образцы — лекция, разделы «Фильтры от фронта: условия, которых заранее нет» и «Проверить то, что прислал фронт». Изменение назови `server-side-filter` — заводит его агент скиллом `openspec-new-change`.

> [!NOTE]
> Клиентская часть здесь намеренно крошечная: значение `hideDone` нужно передать в функцию запроса и добавить в ключ `useQuery`. Оценивается в первую очередь серверная половина. Если начал переписывать компоненты — остановись и перечитай тикет.

> [!TIP] Совет
> Самая вероятная точка, где всё встанет: **фильтр забыт в ключе запроса React Query**. Переключаешь галочку, запрос на сервер не уходит, доска показывает прежний список — и кажется, что сломался сервер. Ключ запроса — это то, по чему React Query отличает один набор данных от другого: если ключ не изменился, он считает, что спрашивать заново нечего, и отдаёт то, что уже лежит в кэше.

> [!TIP] Совет
> Чтобы увидеть, какой запрос на самом деле уходит в базу, временно допиши перед `pool.query` вывод собранного текста и массива значений в консоль. Это законный приём отладки — просто убери его перед сдачей. Так критерий 7 проверяется за десять секунд: включил фильтр — `WHERE` есть, выключил — нет.

**Готово, когда:**

- [ ] на вкладке Network в инструментах разработчика видно, что при переключении фильтра уходит **новый** запрос, и параметр в его адресе меняется;
- [ ] в ответе сервера при включённом фильтре приходят только невыполненные карточки — не все;
- [ ] в коде клиента нет ни одного места, где список карточек отсеивается после получения с сервера;
- [ ] выбранное имя параметра и его допустимые значения зафиксированы в спеке и `design.md` как решение с обоснованием, а не появились по ходу написания кода;
- [ ] негодное значение параметра отвечает `400` (проверь, открыв адрес с ерундой в браузере);
- [ ] когда все карточки выполнены и фильтр включён, доска показывает пустую колонку, а не сообщение об ошибке;
- [ ] внутри текста SQL-запроса нет ни одного `${` — значение уезжает массивом;
- [ ] поиск по проекту слова `SELECT` по-прежнему находит его только в `repositories/`;
- [ ] в `openspec/changes/archive/<дата>-server-side-filter/` лежат все пять файлов: `proposal.md`, спека, `design.md`, `tasks.md`, `report.md`;
- [ ] история коммитов читается как постановка → решение → шаги реализации → архивация;
- [ ] ветка отправлена в твою копию, открыт merge request с описанием: что сделано и как проверить.

**Сдача:** merge request из `feature/server-side-filter` в `main` твоей копии — **не вливай его сам**, его проверяет преподаватель. Приёмка — по зачётной системе курса: все критерии выполнены → зачтено, иначе замечания в MR и доработка до дедлайна (подробнее — в [«Организации работы»](../COURSE-SETUP.md)).

## Частые ошибки — проверь себя перед сдачей

- `.env` попал в коммит вместе с паролем — проверь панель Source Control до того, как нажмёшь «Commit»;
- `npm run db:reset` работает один раз, а на второй падает — в `schema.sql` забыт `DROP TABLE IF EXISTS`;
- Порядок таблиц в `schema.sql` перепутан: `CREATE TABLE cards` стоит раньше `users`, и внешнему ключу не на что ссылаться;
- Забыт `.rows` — `result.map is not a function`; или забыт `await` — `Cannot read properties of undefined`;
- Забыт `.map(toCard)` — фронт получает `is_done` вместо `isDone`, и все карточки выглядят невыполненными; ошибки при этом нет нигде;
- Значение от фронта склеено в текст запроса вместо `$1` — задание не засчитывается независимо от того, работает ли доска;
- Фильтр не добавлен в ключ `useQuery` — переключатель щёлкает, а список не меняется;
- Отбор карточек оставлен и на клиенте «на всякий случай» — критерий 2 не выполнен: работа сделана дважды, и однажды две копии разъедутся;
- Пустой результат отдан как `404` — доска показывает ошибку загрузки там, где просто нет подходящих карточек;
- `id` из адреса ушёл в базу строкой — `DELETE /cards/abc` отвечает `500` вместо `400`;
- `SELECT` найден в сервисе или контроллере — граница слоёв сломана;
- Массив карточек оставлен в сервисе «на всякий случай» — после переезда его быть не должно;
- Рефакторинг «заодно»: вместе с переносом в базу поменялось и поведение. В задании 2 доска обязана работать ровно как раньше;
- Один гигантский коммит на всю задачу вместо последовательности постановка → решение → шаги → архивация;
- Merge request оценочного задания по ошибке открыт в репозиторий курса, а не в свою копию.
