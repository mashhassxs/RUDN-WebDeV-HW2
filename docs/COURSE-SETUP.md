# Организация работы: установка проекта, Git, сдача заданий

Этот документ читается один раз в начале курса, а дальше используется как справочник. Здесь описано: как завести себе копию проекта, как работать с Git без командной строки и как сдаются и принимаются задания. В самих семинарах эти вещи не повторяются.

## Сквозной проект

На этом курсе ты ведёшь **один проект — канбан-доску** — от первого семинара до последнего. Каждая тема добавляет к проекту новый слой: сначала клиент на React, дальше — сервер, база данных, авторизация. Проект живёт в твоей копии репозитория весь семестр, и работа с ним ведётся так, как принято в командной разработке: ветка на задачу, осмысленные коммиты, merge request.

Репозиторий курса: **https://github.com/GurinSimon/RUDN-WebDev-Advanced**. Он устроен так:

```
client/     # фронтенд на React — с ним работаем с темы 1
server/     # бэкенд на Express — пока пуст, наполним в теме 3
docs/       # лекции и задания семинаров
openspec/   # спеки и задачи для работы с AI-агентом (тема 2)
```

`client/` и `server/` — два самостоятельных проекта, каждый со своим `package.json` и своими зависимостями; общаются они между собой только по HTTP. Поэтому команды вроде `npm install` выполняются не в корне репозитория, а внутри той папки, к которой относятся.

Папки `docs/` и `openspec/` лежат в корне, а не внутри `client/` или `server/`: материалы курса нужны независимо от того, какую часть проекта ты сейчас правишь, а задача может затрагивать сразу обе.

## Как устроены семинары

Каждая тема курса занимает две субботы: на первой — лекция и семинар 1, на второй — семинар 2 (расписание — в [плане курса](COURSE-PLAN.md)). Заданий у темы **три**:

- **Задания 1 и 2 — промежуточные** (семинар 1). Небольшие и намеренно простые: каждое тренирует один конкретный навык, без которого не выполнить третье. Они не оцениваются, но выполняются обязательно — оценочное задание строится на их результате.
- **Задание 3 — оценочное** (семинар 2). Оформлено как рабочий тикет — задача в том виде, в каком её получает джуниор-разработчик в команде: описание, критерии приёмки, сдача через merge request.

У каждого задания есть список **«Готово, когда»** — по нему ты проверяешь себя сам, а преподаватель проверяет работу.

Проверить, что всё встало, можно одной серией команд в терминале — каждая должна напечатать номер версии, а не «команда не найдена»:

```bash
node --version     # v22.18.0 или новее
npm --version
git --version
psql --version     # psql (PostgreSQL) 17.x — после установки PostgreSQL
docker --version   # после установки Docker Desktop
```

> [!IMPORTANT]
> Версия Node именно **не ниже 22.18** — на более старых сервер курса просто не запустится: начиная с этой версии Node умеет выполнять файлы TypeScript напрямую, и весь серверный код курса на это рассчитан. Если `node --version` показывает что-то меньшее — поставь свежую LTS с [nodejs.org](https://nodejs.org/) поверх, ничего удалять не нужно.

> [!TIP]
> Мелочи, на которых обычно теряют время:
>
> - **PostgreSQL на Windows** при установке просит придумать пароль — **запиши его сразу**, он понадобится в теме 5 и восстановлению не подлежит;
> - **`psql: команда не найдена`** после установки означает лишь, что программа не попала в `PATH`: на Windows её видно в меню «Пуск» как **SQL Shell (psql)**, на macOS путь добавляется в настройках Postgres.app;
> - **Docker Desktop на Windows** требует включённого WSL2 — установщик предложит это сам и попросит перезагрузку;
> - **Библиотеки проекта** (`express`, `pg`, `bcryptjs` и прочие) заранее ставить не надо: они появляются по ходу семинаров командой `npm install` и всегда внутри `client/` или `server/`.

## Как завести проект себе

Репозиторий курса живёт на GitHub, но работать ты будешь в **собственной копии** — на той платформе, где у тебя есть аккаунт. Копия должна быть **публичной**, иначе преподаватель не увидит твою работу.

### Если у тебя аккаунт GitHub — форк

1. Открой https://github.com/GurinSimon/RUDN-WebDev-Advanced;
2. Нажми «Fork» (кнопка в правом верхнем углу) → в поле «Owner» выбери свой аккаунт → «Create fork».

Готово: твоя копия — `github.com/твой-логин/RUDN-WebDev-Advanced`. Форк публичный по умолчанию — таким и оставь.

### Если у тебя аккаунт GitLab — импорт

Форкнуть проект с GitHub на GitLab нельзя, но GitLab умеет заводить проект из чужого репозитория, забирая его целиком:

1. Открой https://gitlab.com/projects/new#import_project;
2. Среди способов импорта выбери «Repository by URL»;
3. В поле «Git repository URL» вставь `https://github.com/GurinSimon/RUDN-WebDev-Advanced.git`;
4. Ниже укажи имя проекта (оставь `RUDN-WebDev-Advanced`) и видимость **Public**;
5. Нажми «Create project» и подожди пару минут.

Готово: твоя копия — `gitlab.com/твой-логин/RUDN-WebDev-Advanced`. Это полноценный самостоятельный репозиторий со всей историей коммитов.

### Клонирование и запуск

1. Скопируй адрес **своей копии**: на её странице нажми синюю кнопку «Code» → скопируй HTTPS-URL;
2. В VS Code открой панель Source Control (значок с ветками слева, `Ctrl+Shift+G`) → «Clone Repository» → вставь адрес → выбери папку на диске;
3. Открой терминал (меню Терминал → Создать терминал) и перейди в папку клиента: `cd client` — все команды ниже выполняются оттуда, потому что `package.json` клиента лежит именно там;
4. `npm install` — один раз после клонирования;
5. `npm run dev` — приложение откроется на `http://localhost:5173`;
6. Для заданий тем 1–2, где нужен мок-сервер, — `npm run server` во **втором** терминале (кнопка «+» на панели терминала), не забыв и там сначала перейти в `client`.

> [!NOTE]
> Начиная с темы 3 мок-сервер заменяется настоящим, который ты напишешь сам, и запускается он по-другому: во втором терминале `cd server`, а затем `npm run dev`. Своя папка — свой `package.json` — свои команды; подробности будут в самой теме.

> [!TIP] Если у тебя macOS
>
> - Git не установлен из коробки: при первом обращении VS Code к Git система сама предложит поставить «Command Line Developer Tools» — нажми «Install» и подожди несколько минут;
> - Горячие клавиши: консоль браузера — `Cmd+Option+I` вместо `F12`; обновить страницу — `Cmd+R` вместо `F5`; панель Source Control — та же `Ctrl+Shift+G`.
>
> Всё остальное — кнопки VS Code, npm-команды, работа с GitHub/GitLab — выглядит и работает одинаково на Windows и macOS.

## Git без командной строки

Все операции с Git в этом курсе делаются мышкой — через интерфейс VS Code и сайт GitHub/GitLab. Понадобятся ровно четыре:

1. **Создать ветку.** В левом нижнем углу VS Code (статус-бар) написано имя текущей ветки (`main`). Нажми на него → «Create new branch…» → введи имя ветки.
2. **Закоммитить.** Панель Source Control (`Ctrl+Shift+G`): наведись на изменённые файлы и нажми «+» (Stage Changes), впиши сообщение коммита в поле сверху, нажми «Commit».
3. **Отправить в свою копию.** Кнопка «Publish Branch» (для новой ветки) или «Sync Changes» (для уже отправленной) в той же панели.
4. **Открыть merge request.** Открой свою копию в браузере — после отправки ветки появится плашка: на GitHub «Compare & pull request», на GitLab «Create merge request». Нажми её и подтверди создание. Влить — кнопка «Merge» на странице MR.

> [!NOTE]
> **Merge Request (MR)** на GitLab и **Pull Request (PR)** на GitHub — это одно и то же: предложение влить ветку с проверкой изменений. В материалах курса используется «merge request»; если ты на GitHub — читай это как «pull request».

> [!WARNING]
> Только для тех, кто на GitHub с форком: при создании pull request GitHub по умолчанию предлагает влить твою ветку **в репозиторий курса**, а не в твой форк. На странице создания PR слева есть выпадающий список «base repository» — проверяй, что там выбрана **твоя копия** (`твой-логин/RUDN-WebDev-Advanced`), а не `GurinSimon/...`. У тех, кто завёл проект импортом на GitLab, этой ловушки нет — импортированный репозиторий ни с чем не связан.

Два железных правила на весь курс:

- в `main` напрямую не работаем — на каждое задание своя ветка;
- сообщение коммита описывает изменение: `feat: add isDone to BoardCard` — да, `fix2` и `сделал всё` — нет.

## Как получить новые материалы

Лекции и семинары выкладываются по ходу семестра: когда ты заводил свою копию, материалов последних тем в ней ещё не было. Сама по себе копия не обновляется — новые лекции нужно забрать из репозитория курса.

Это единственное место, где понадобится терминал: кнопки для такой операции в VS Code нет. Обе команды выполняются из **корня** репозитория — если терминал сейчас внутри `client/` или `server/`, вернись командой `cd ..`.

**Один раз**, сразу после клонирования, — привяжи репозиторий курса к своей копии под именем `course`:

```bash
git remote add course https://github.com/GurinSimon/RUDN-WebDev-Advanced.git
```

**Каждый раз, когда преподаватель объявил о новых материалах**, — забери свежую папку `docs/`:

```bash
git fetch course
git checkout course/main -- docs/
```

После этого обновлённые файлы появятся в панели Source Control как обычные изменения — закоммить их сообщением вроде `docs: материалы темы 5` и отправь в свою копию.

> [!NOTE]
> Забирается **только папка `docs/`**. Твой код — `client/`, `server/`, `openspec/` — этими командами не затрагивается, поэтому потерять свою работу при обновлении невозможно. Конфликтов здесь тоже не бывает: материалы курса правит только преподаватель, а ты их читаешь.

> [!TIP]
> Адрес в первой команде — это адрес **репозитория курса**, а не твоей копии, и он одинаков для всех. Неважно, форкнул ты проект на GitHub или завёл импортом на GitLab: в обоих случаях команда одна и та же.

По профилю преподаватель находит твою копию проекта и видит всю активность: коммиты, ветки и merge request'ы — как по семинарам, так и по домашним заданиям;
- Оценочное задание считается сданным, когда в твоей копии открыт оформленный MR (что сделано, как проверить). Этот MR **не вливается** — его проверяет преподаватель. Отдельно отправлять ссылку на него не нужно;
- Дедлайн каждого семинара указан в самом семинаре.

### Как принимается работа

Оценка бинарная — **зачтено / не зачтено**, частичных баллов нет. Работает это как код-ревью в команде:

- **Зачтено** — выполнены все критерии приёмки тикета и Git-требования: работа в отдельной ветке, осмысленные коммиты, оформленный MR в своей копии;
- **Не зачтено** — преподаватель оставляет замечания комментариями прямо в MR и возвращает работу на доработку. Исправь замечания в той же ветке, отправь изменения («Sync Changes») и напиши в MR комментарий, что работа готова к перепроверке;
- Кругов доработки может быть **сколько угодно** — пока преподаватель оставляет замечания и требует исправлений, работа дорабатывается и перепроверяется. Ограничение одно: дедлайн. После дедлайна результат фиксируется как есть.
