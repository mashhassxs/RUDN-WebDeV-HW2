# Тема 6. Семинар: вход в приложение и защита доски

> **Организационное примечание.** Семинар и лекция по этой теме проходят в один день, порядок может отличаться. В каждом задании указано, в каком разделе лекции ([LECTURE-6.md](LECTURE-6.md)) лежит нужный образец кода, — если семинар у тебя идёт первым, открывай лекцию прямо по ходу работы.

> [!IMPORTANT] Проверь перед началом
> Весь семинар строится на базе из прошлой темы: таблицы `users` и `cards`, репозиторий, `npm run db:reset`. Если оценочное задание темы 5 не сдано или возвращено на доработку — закрой сначала его: приделывать пароли будет не к чему.

**Дедлайн сдачи семинара:** первое занятие Темы 8.

## Перед началом: чем проверять то, у чего нет кнопки

До сегодняшнего дня всё, что ты писал на сервере, можно было проверить прямо на доске: создал карточку — она появилась. Сегодня появятся регистрация и вход, а кнопок для них на доске нет и в этой теме не будет. Значит, нужен способ отправить запрос руками.

Такой способ уже есть, ставить ничего не надо — **консоль браузера**. Открой доску на `http://localhost:5173`, нажми `F12` (на macOS `Cmd+Option+I`), перейди на вкладку Console и выполняй запросы прямо там:

```javascript
(
  await fetch("/api/auth/register", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email: "test@example.com", password: "test1234" }),
  })
).status;
```

В ответ консоль напечатает число — статус-код. Именно его ты и проверяешь в заданиях: `201`, `400`, `401`, `409`. Чтобы увидеть не код, а тело ответа, замени `.status` на `.json()`:

```javascript
await (await fetch("/api/cards")).json();
```

Три вещи, на которых здесь спотыкаются:

- **Консоль должна быть открыта на вкладке с доской** (`localhost:5173`), а не на пустой вкладке или на странице поисковика. Короткий адрес `/api/...` означает «на том же сайте, что и страница» — на чужой странице ему некуда вести;
- **Заголовок `Content-Type` обязателен.** Без него `express.json()` не станет разбирать тело, `req.body` окажется пустым, и сервер ответит ошибкой на совершенно правильный запрос;
- **Результат виден и на вкладке Network** — там же видно, что именно ушло и что вернулось. Когда ответ непонятен, смотри туда, а не гадай.

> [!TIP] Совет
> Cookie, которую сервер поставит при входе, браузер запомнит для всей вкладки. Это значит, что войти достаточно **один раз**: дальше и запросы из консоли, и сама доска будут ходить на сервер уже от твоего имени, пока не истечёт срок или ты не выйдешь.

## Задание 1 (промежуточное). Пароль, который нельзя прочитать

**Навык:** хеширование пароля через bcrypt, столбцы для входа, регистрация по слоям.
**Ветка:** `feature/password-hashing`.

Образцы — лекция, разделы «bcrypt на практике», «Что добавляется в схему», «Начальные данные с паролем» и «Регистрация: новый пользователь».

1. Создай ветку `feature/password-hashing` от `main`.
2. В `server/db/schema.sql` добавь таблице `users` два столбца: `password_hash TEXT NOT NULL` и `role` со списком допустимых значений и значением по умолчанию `'user'`.
3. В `server/db/seed.sql` заведи двух пользователей — Анну с ролью `user` и Бориса с ролью `moderator`, обоим готовый хеш из лекции (ему соответствует пароль `qwerty123`). Там же **отдай одну из трёх карточек Борису** — владелец ищется подзапросом по почте, как в теме 5. Чужая карточка понадобится в оценочном задании.
4. Выполни `npm run db:reset` и посмотри, что легло в базу:

```bash
psql -d kanban -c "SELECT email, role, password_hash FROM users;"
```

В столбце `password_hash` должна стоять строка ровно на 60 символов, начинающаяся с `$2b$10$`. Ни на что читаемое она не похожа — так и должно быть.

5. Поставь библиотеку: `npm install bcryptjs`, а типы к ней — `npm install --save-dev @types/bcryptjs`.
6. Напиши регистрацию по слоям, снизу вверх:
   - `repositories/users.repository.ts` — кладёт нового пользователя в таблицу и возвращает его же, уже с присвоенным `id`. Отдельно обрабатывается один случай: почта в схеме объявлена `UNIQUE`, поэтому на вторую регистрацию с той же почтой ошибку выдаёт **база**, а не твой код. Ошибка эта ожидаемая — «такой пользователь уже есть» не поломка сервера, — поэтому репозиторий её ловит по коду `23505` (тот же приём, что в теме 5) и возвращает `null`. Выше по слоям этот `null` превратится в понятный ответ `409`, а не в `500`;
   - `services/auth.service.ts` — считает хеш через `bcrypt.hash(password, 10)` и зовёт репозиторий;
   - `controllers/auth.controller.ts` — `201` с пользователем или `409`, если сервис вернул `null`;
   - `middleware/validateCredentials.ts` — почта похожа на почту, пароль не короче восьми символов, иначе `400`;
   - `routes/auth.routes.ts` — роут `POST /register` с валидацией перед контроллером; роутер подключается в `index.ts` строкой `app.use("/auth", authRouter)`.
7. Проверь работу из консоли браузера — три запроса подряд:

```javascript
// новый пользователь — ждём 201
(
  await fetch("/api/auth/register", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email: "ivan@example.com", password: "test1234" }),
  })
).status;
```

Повтори тот же запрос второй раз, ничего не меняя, — теперь должно прийти `409`. Затем отправь третий: почту подставь любую новую, а пароль — `"123"`. Должно прийти `400`, и до базы этот запрос не доедет вовсе: его развернёт валидация.

8. Зарегистрируй тем же запросом **второго** пользователя — `petr@example.com`, и пароль ему задай **тот же самый**, `test1234`. А теперь загляни в базу:

```bash
psql -d kanban -c "SELECT email, password_hash FROM users;"
```

Найди в выводе строки Ивана и Петра: пароль у них одинаковый, а хеши в таблице **разные**. Это и есть соль из лекции в действии — перед хешированием bcrypt подмешивает к паролю случайную строку и кладёт её тут же, внутрь результата. Самого пароля `test1234` в таблице нет ни в одной строке, и получить его обратно из хеша нельзя.

**Готово, когда:**

- [ ] `npm run db:reset` отрабатывает дважды подряд, в `users` два пользователя, у одного роль `moderator`;
- [ ] одна из трёх карточек принадлежит Борису — видно запросом `SELECT title, owner_id FROM cards;`;
- [ ] в столбце `password_hash` строка на 60 символов, начинающаяся с `$2b$10$`;
- [ ] регистрация нового пользователя отвечает `201`, повтор с той же почтой — `409`, пароль короче восьми символов — `400`;
- [ ] у двух пользователей с одинаковым паролем в базе лежат **разные** хеши;
- [ ] в ответе на регистрацию **нет** поля с хешем — проверь на вкладке Network;
- [ ] поиск по проекту не находит ни одного места, где пароль записывается в базу или в лог как есть;
- [ ] в ветке отдельные коммиты: схема и данные, репозиторий, сервис с хешированием, контроллер и роут.

> [!WARNING] Предостережение
> Самая коварная ошибка этого задания — **забытый `await` перед `bcrypt.hash`**. Ошибки не будет нигде: в базу уедет строка `[object Promise]`, регистрация ответит `201`, и всё будет выглядеть работающим ровно до попытки войти. Если в столбце `password_hash` не строка на `$2b$10$`, а что-то другое — причина здесь.

> [!TIP] Совет
> Хеш для своего пароля считается одной командой из папки `server/` — если захочется положить в `seed.sql` не `qwerty123`:
>
> ```bash
> node -e "import('bcryptjs').then(b => b.default.hash('мой-пароль', 10).then(console.log))"
> ```

## Задание 2 (промежуточное). Вход, токен и cookie

**Навык:** выпуск JWT, секрет в `.env`, cookie с `httpOnly`, чтение cookie на сервере.
**Ветка:** `feature/login-jwt`.

Сначала Git: влей `feature/password-hashing` в `main` своей копии, переключись на `main`, нажми «Sync Changes» и создай ветку `feature/login-jwt`.

Образцы — лекция, разделы «JWT: что за строка приезжает после входа», «Выпуск и проверка токена», «Вход: проверка пароля» и «Как токен ездит между клиентом и сервером».

1. Поставь три пакета: `npm install jsonwebtoken cookie-parser`, к ним типы — `npm install --save-dev @types/jsonwebtoken @types/cookie-parser`.
2. Допиши в `server/.env` ключ `JWT_SECRET` с длинной случайной строкой, а в `server/.env.example` — тот же ключ с фиктивным значением. В репозиторий уезжает только второй файл.
3. Создай `server/token.ts` с двумя функциями: `createToken` (подписывает `sub` и `role`, срок — два часа) и `readToken` (проверяет подпись и срок).
4. Добавь в `users.repository.ts` функцию `findByEmailWithHash` — единственную во всём проекте, которая достаёт хеш наружу. Длинное имя не сокращай, оно и есть предупреждение.
5. Напиши вход в `auth.service.ts`: нашёл пользователя, сравнил пароль через `bcrypt.compare`, выдал токен. Обе неудачи — «нет такой почты» и «пароль не тот» — возвращают **одно и то же**.
6. В `auth.controller.ts` положи токен в cookie и ответь пользователем:

```typescript
res.cookie("token", result.token, AUTH_COOKIE);
res.json(result.user);
```

Константу `AUTH_COOKIE` с настройками `httpOnly`, `sameSite` и `maxAge` возьми из лекции. `secure: true` не ставь — на `http://localhost` браузер такую cookie молча выбросит.

7. Подключи в `index.ts` чтение cookie — `app.use(cookieParser())`, рядом с `express.json()` и **выше** роутов.
8. Добавь выход — `POST /auth/logout`, внутри `res.clearCookie("token")` и ответ `204`.
9. Проверь вход из консоли браузера:

```javascript
(
  await fetch("/api/auth/login", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email: "anna@example.com", password: "qwerty123" }),
  })
).status;
```

10. А теперь посмотри на то, что выдал сервер. DevTools → вкладка **Application** → слева **Cookies** → `http://localhost:5173`. Там лежит `token`, у него стоит галочка `HttpOnly`, и виден срок. Выполни в консоли `document.cookie` — токена в выводе нет, хотя он только что появился в списке cookie. Это и есть `httpOnly`.
11. Скопируй значение токена и вставь его на [jwt.io](https://jwt.io/). Сайт разберёт строку на три части и покажет `sub`, `role`, `iat` и `exp` — без всякого секрета. Убедись, что `sub` — это `id` того пользователя, которым ты вошёл, а пароля внутри нет.

**Готово, когда:**

- [ ] вход с верным паролем отвечает `200`, и в списке cookie появляется `token` с галочкой `HttpOnly`;
- [ ] вход с неверным паролем и вход с незарегистрированной почтой отвечают **одинаково** — `401` и один и тот же текст;
- [ ] `document.cookie` в консоли токен не показывает;
- [ ] содержимое токена читается на jwt.io: внутри `sub` и `role`, пароля и хеша нет;
- [ ] `POST /api/auth/logout` отвечает `204`, после него строка `token` из списка cookie пропадает;
- [ ] `JWT_SECRET` есть в `.env`, `.env` не попал в коммит, а `.env.example` — попал;
- [ ] в ветке отдельные коммиты: токены, вход, cookie и выход.

> [!TIP] Совет
> `secretOrPrivateKey must have a value` при попытке войти — забыт `JWT_SECRET` в `.env` или флаг `--env-file=.env` в скрипте `dev`. Про `.env` в этом сообщении не сказано ни слова, поэтому запомни его вид заранее.

## Задание 3 (оценочное). Тикет KAN-6

Задача целиком по конвейеру: разведка, постановка (`proposal.md` и спека), `design.md` и `tasks.md`, реализация по шагам, архивация. Предмет — то, ради чего писались первые два задания: вход наконец начинает что-то значить.

Влей `feature/login-jwt` в `main` своей копии и создай ветку `feature/protect-cards`.

> **KAN-6: Карточки на доске может создать и удалить кто угодно**
>
> Доска переехала в базу, у карточек есть владелец — и при этом автором любой новой карточки становится один и тот же пользователь из константы `CURRENT_USER_ID`, а удалить карточку может любой, кто отправит запрос. Кнопки на доске тут ни при чём: запрос `DELETE /cards/42` отправляется из консоли браузера за секунду, и сервер его выполнит, кто бы его ни прислал.
>
> Вход в приложение уже написан, но на карточки он никак не влияет.
>
> **Критерии приёмки:**
>
> 1. Чтение доски остаётся открытым: `GET /cards` без входа отвечает `200` и показывает карточки;
> 2. Всё, что меняет данные, требует входа: без cookie сервер отвечает `401`;
> 3. Автор новой карточки берётся из токена. Константы `CURRENT_USER_ID` в проекте не остаётся, поле вроде `ownerId` в теле запроса не читается;
> 4. Удалить карточку может её владелец. Чужая — `403`, и карточка остаётся в базе;
> 5. Пользователь с ролью `moderator` может удалить любую карточку;
> 6. Несуществующая карточка — `404`, а не `403`; негодный `id` в адресе — `400`;
> 7. Решение «кто пришёл» принимает промежуточная функция, решение «его ли это карточка» — сервис; контроллер только переводит ответ сервиса в статус-код.

Образцы — в лекции: раздел про `requireAuth`, «Главное правило темы» и раздел про три уровня проверки прав. Изменение назови `protect-cards` — заводит его агент скиллом `openspec-new-change`.

> [!NOTE]
> Эндпоинт `GET /auth/me` из лекции в этом задании не нужен: доска про вошедшего пользователя пока ничего не спрашивает. Он понадобится, когда у клиента появится форма входа.

> [!IMPORTANT] Что произойдёт с доской
> Как только задание заработает, доска для невошедшего перестанет создавать карточки — и это правильный результат, а не поломка. Войди один раз из консоли (запрос из задания 2), обнови страницу — и доска работает как раньше, потому что cookie браузер прикладывает сам. Через два часа или после выхода всё повторится: карточки видно, создать нельзя.
>
> Клиент в этой теме не трогаем — ни формы входа, ни обработки `401` на нём не появляется.

**Готово, когда:**

- [ ] `(await fetch("/api/cards")).status` без входа возвращает `200`;
- [ ] создание карточки без входа возвращает `401` — проверь тем же запросом из консоли, что и в задании 1, но на адрес `/api/cards`;
- [ ] после входа Анной создание работает, и у новой карточки в базе `owner_id` равен `id` Анны, а не единице «по умолчанию»: `psql -d kanban -c "SELECT title, owner_id FROM cards;"`;
- [ ] поиск по проекту не находит `CURRENT_USER_ID`;
- [ ] войдя Анной, попробуй удалить карточку Бориса — `403`, и после этого карточка по-прежнему в базе;
- [ ] войдя Борисом (`boris@example.com`, `qwerty123`), удали ту же чужую карточку — `204`;
- [ ] удаление несуществующей карточки (`/api/cards/999`) отвечает `404`, а `/api/cards/abc` — `400`;
- [ ] в файле роутов видно построчно, что открыто, а что закрыто; проверка владения при этом в роутах не упоминается — она в сервисе;
- [ ] `requireAuth` стоит **перед** валидацией и контроллером во всех строках, где он есть;
- [ ] в `openspec/changes/archive/<дата>-protect-cards/` лежат все пять файлов: `proposal.md`, спека, `design.md`, `tasks.md`, `report.md`;
- [ ] история коммитов читается как постановка → решение → шаги реализации → архивация;
- [ ] ветка отправлена в твою копию, открыт merge request с описанием: что сделано и как проверить.

> [!TIP] Совет
> Проверять удобнее всего парами «до и после входа». Открой две вкладки консоли по очереди: в первой выполни запрос без входа и запиши код ответа, потом войди и повтори тот же запрос. Если оба раза приходит одно и то же — либо `requireAuth` не стоит на роуте, либо стоит, но ниже обработчика.

> [!TIP] Совет
> `403` вместо ожидаемого `204` при удалении **своей** карточки означает, что сравниваются разные вещи: в токене `sub` лежит строкой, а `owner_id` из базы приходит числом. `"1" === 1` — ложь. В лекции поэтому и стоит `Number(payload.sub)`.

**Сдача:** merge request из `feature/protect-cards` в `main` твоей копии — **не вливай его сам**, его проверяет преподаватель. Приёмка — по зачётной системе курса: все критерии выполнены → зачтено, иначе замечания в MR и доработка до дедлайна (подробнее — в [«Организации работы»](../COURSE-SETUP.md)).

## Частые ошибки — проверь себя перед сдачей

- Забыт `await` перед `bcrypt.hash` — в базе `[object Promise]` вместо хеша, регистрация при этом отвечает `201`;
- Забыт `await` перед `bcrypt.compare` — в `if` попадает промис, который всегда истинен: **вход пускает с любым паролем**. Проверь специально: войди с заведомо неверным паролем и убедись, что пришёл `401`;
- Хеш уехал фронту — `SELECT *` в репозитории или `return result.rows` без перевода строки в объект;
- Ответы на «нет такой почты» и «неверный пароль» разные — сервер сам рассказывает, кто у него зарегистрирован;
- Забыт `app.use(cookieParser())` — любой закрытый эндпоинт падает в `500` с сообщением `Cannot read properties of undefined (reading 'token')`, где про cookie ни слова;
- `cookieParser()` подключён ниже роутов — до тех, что объявлены выше него, он не доберётся;
- В настройках cookie оставлен `secure: true` — вход отвечает `200`, cookie не появляется, следующий запрос снова `401`, и ошибок нет нигде;
- Cookie поставлена без `httpOnly` — работает так же, защищает уже нет;
- `.env` попал в коммит вместе с секретом — проверь панель Source Control до того, как нажмёшь «Commit»;
- `JWT_SECRET` вписан прямо в `token.ts` «чтобы пока работало» — задание не засчитывается: секрет в публичном репозитории означает, что токен модератора выпишет себе любой читатель;
- `jwt.verify` вызван без `try`/`catch` — просроченный токен роняет запрос в `500` вместо честного `401`;
- `CURRENT_USER_ID` остался в сервисе — карточки по-прежнему создаются от имени одного человека, критерий 3 не выполнен;
- `ownerId` читается из тела запроса — автором карточки можно назначить кого угодно;
- `requireAuth` забыт на одном из роутов — девять эндпоинтов закрыты, десятый открыт настежь; поэтому файл роутов и читают целиком, построчно;
- Проверка владения не написана вовсе — «вошёл значит можно всё»: критерий 4 не выполнен, хотя `401` больше не приходит;
- Проверка владения написана в контроллере или в middleware — чтобы её сделать, нужна сама карточка из базы, а это работа сервиса;
- Несуществующая карточка отвечает `403` вместо `404` — проверка владения выполняется раньше проверки существования;
- `403` при удалении своей карточки — сравнивается строка из токена с числом из базы;
- `401` и `403` перепутаны местами — по ответу невозможно понять, входить заново или не лезть;
- Один гигантский коммит на всю задачу вместо последовательности постановка → решение → шаги → архивация;
- Merge request оценочного задания по ошибке открыт в репозиторий курса, а не в свою копию.
