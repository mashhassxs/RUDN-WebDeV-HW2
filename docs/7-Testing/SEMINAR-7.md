# Тема 7. Семинар: доказать, что защита доски работает

> **Организационное примечание.** Семинар и лекция по этой теме проходят в один день, порядок может отличаться. В каждом задании указано, в каком разделе лекции ([LECTURE-7.md](LECTURE-7.md)) лежит нужный образец кода, — если семинар у тебя идёт первым, открывай лекцию прямо по ходу работы.

> [!IMPORTANT] Проверь перед началом
> Весь семинар строится на коде прошлой темы: вход по токену в cookie, `requireAuth` на закрытых роутах, проверка владения в сервисе. Если оценочное задание темы 6 не сдано или возвращено на доработку — закрой сначала его: сегодня мы ничего не добавляем, мы доказываем, что уже написанное работает.

**Дедлайн сдачи семинара:** две недели с даты занятия.

---

## Перед началом

Сегодня в доске не появится ни одной новой возможности. Ни эндпоинта, ни кнопки — пользователь не заметит вообще ничего. Появится другое: **способ за полсекунды убедиться, что всё написанное за шесть тем по-прежнему работает**.

Звучит скромно ровно до первого раза, когда это спасёт. Вспомни ошибку из прошлой темы: `requireAuth`, забытый на одном роуте из десяти. Сервер работает, доска открывается, ошибок нет нигде — и любой желающий удаляет чужие карточки. Сегодня ты напишешь проверку, которая находит такое сама, при каждом запуске.

Понадобится поставить две вещи: программу Insomnia (задание 1) и пару пакетов в `server/` (задание 2). Всё остальное у тебя уже есть. Команды, как и всю прошлую тему, выполняем **из папки `server/`**.

## Задание 1 (промежуточное). Insomnia вместо консоли браузера

**Навык:** коллекция запросов, окружение с переменными, cookie после входа, прогон коллекции.
**Ветка:** `feature/insomnia-collection`.

Образцы — лекция, раздел «Ручной клиент вместо консоли: Insomnia».

1. Создай ветку `feature/insomnia-collection` от `main`.
2. Поставь Insomnia с [insomnia.rest/download](https://insomnia.rest/download). Аккаунт заводить не нужно: при первом запуске выбери работу без входа (локальное хранилище) — всё, что мы делаем, лежит на твоём компьютере.
3. Подними то, что будешь проверять: `npm run db:reset`, затем `npm run dev` в отдельном терминале.
4. Create → Collection, назови «Канбан». Внутри заведи две папки: `auth` и `cards`.
5. В настройках окружения коллекции задай переменную:

```json
{
  "baseUrl": "http://localhost:3001"
}
```

6. Собери **семь запросов**. Адрес везде пишется через переменную — `{{ _.baseUrl }}/cards`, а не строкой (набирать скобки руками не нужно: `Ctrl+Space` в поле адреса подставит):

| Папка   | Метод    | Адрес                        | Тело (JSON)                                              |
| ------- | -------- | ---------------------------- | -------------------------------------------------------- |
| `auth`  | `POST`   | `{{ _.baseUrl }}/auth/register` | `{ "email": "ivan@example.com", "password": "test1234" }` |
| `auth`  | `POST`   | `{{ _.baseUrl }}/auth/login`    | `{ "email": "anna@example.com", "password": "qwerty123" }` |
| `auth`  | `POST`   | `{{ _.baseUrl }}/auth/logout`   | —                                                          |
| `cards` | `GET`    | `{{ _.baseUrl }}/cards`         | —                                                          |
| `cards` | `POST`   | `{{ _.baseUrl }}/cards`         | `{ "title": "Карточка из Insomnia" }`                      |
| `cards` | `DELETE` | `{{ _.baseUrl }}/cards/1`       | — (карточка Анны)                                          |
| `cards` | `DELETE` | `{{ _.baseUrl }}/cards/3`       | — (карточка Бориса)                                        |

> [!WARNING] Предостережение
> Адрес — `http://localhost:3001`, **без `/api`**. В консоли браузера ты писал `/api/cards`, потому что страница открыта на порту 5173 и запрос перехватывал прокси Vite, отрезая `/api` по дороге. Insomnia стучится прямо в сервер, никакого прокси перед ней нет. Оставишь `/api` — получишь `404` от собственного обработчика «такого пути нет» и будешь искать ошибку в роутере, которого она не касается.

7. Теперь пройди тот же порядок, что в семинаре прошлой темы, — но уже сохранёнными запросами:
   - `GET /cards` — `200`, доска видна без всякого входа;
   - `POST /cards` — `401`, потому что ты ещё не вошёл;
   - `POST /auth/login` Анной — `200`;
   - `POST /cards` — теперь `201`. Ты ничего не прикладывал к запросу руками: cookie приложила сама Insomnia;
   - `DELETE /cards/3` (карточка Бориса) — `403`;
   - `POST /auth/logout` — `204`;
   - `POST /cards` — снова `401`.
8. Загляни в менеджер cookie (рядом с настройками окружения): там лежит `token` с пометкой `httpOnly` — та самая, которую ставил твой сервер.
9. Выгрузи коллекцию в репозиторий: Export → формат Insomnia v5 (YAML) → сохрани файл в корень папки `server/` под именем `kanban.insomnia.yaml`. Закоммить его.

**Готово, когда:**

- [ ] в коллекции семь запросов, разложенных по папкам `auth` и `cards`;
- [ ] адрес во всех запросах записан через `{{ _.baseUrl }}`, а не строкой;
- [ ] `POST /cards` без входа отвечает `401`, а после входа Анной — `201`;
- [ ] удаление карточки Бориса из-под Анны отвечает `403`;
- [ ] после `logout` создание снова отвечает `401`;
- [ ] в менеджере cookie видно `token` с пометкой `httpOnly`;
- [ ] файл `server/kanban.insomnia.yaml` лежит в репозитории, ветка отправлена в твою копию.

> [!TIP] Совет
> `400` с жалобой на отсутствующий `title` при явно заполненном теле означает, что тип тела задан не тот: в выпадающем списке рядом с полем тела должен стоять **JSON**, а не Plain Text. Тогда Insomnia сама пришлёт заголовок `Content-Type: application/json`, без которого `express.json()` не станет разбирать тело, — та же ошибка, что и с забытым заголовком в консоли браузера.

## Задание 2 (промежуточное). Первый тест, который выполняется сам

**Навык:** отдельная тестовая база, обвязка Vitest, разделение `app.ts` и `index.ts`, юнит-тест и первый тест ручки.
**Ветка:** `feature/vitest-setup`.

Сначала Git: влей `feature/insomnia-collection` в `main` своей копии, переключись на `main`, нажми «Sync Changes» и создай ветку `feature/vitest-setup`.

Образцы — лекция, разделы «Тесты в коде: Vitest», «Отдельная база и отдельный секрет», «Первый тест: одна функция» и «Одна правка в проекте: `app.ts` отдельно от `index.ts`».

1. Создай тестовую базу — той же командой, которой в теме 5 создавал рабочую:

```bash
psql -c "CREATE DATABASE kanban_test;"
```

2. Заведи `server/.env.test` с адресом **тестовой** базы и собственным секретом:

```
DATABASE_URL=postgres://kanban_user:secret@localhost:5432/kanban_test
JWT_SECRET=тестовый-секрет-он-же-не-настоящий
```

> [!WARNING] Предостережение
> Допиши `.env.test` в `.gitignore` **прямо сейчас**, до первого коммита, — там пароль от базы, ровно как в `.env` из темы 5. В `.env.example` рядом добавь строчку-подсказку, что такой файл нужен.

3. Поставь пакеты:

```bash
npm install --save-dev vitest supertest @types/supertest
```

4. Заведи два файла обвязки — `vitest.config.ts` и `tests/setup.ts` (оба из лекции). В `setup.ts` обязательно должен быть предохранитель, который останавливает прогон, если в `DATABASE_URL` не тестовая база.
5. Добавь в `package.json` команды `test` и `test:watch`.
6. Раздели `index.ts` на два файла: сборка приложения переезжает в `app.ts` и экспортируется оттуда, в `index.ts` остаётся только `app.listen`. Логгер оберни условием `if (process.env.NODE_ENV !== "test")`, иначе отчёт о тестах утонет в строчках запросов.
7. Напиши `tests/token.test.ts` — два теста на `createToken` и `readToken` из темы 6. Прогони:

```bash
npm test
```

Должно быть две зелёные строки.

8. **Сломай тест намеренно.** Поменяй в первом тесте ожидаемое `"7"` на `"8"`, прогони ещё раз и прочитай отчёт: какой тест упал, что ожидалось, что пришло, на какой строке. Верни как было.

> [!IMPORTANT] Важно
> Этот шаг не формальность и не тратится впустую. Тест, который ты ни разу не видел красным, ничего не доказал: он может проходить потому, что код работает, а может — потому что не проверяет ничего. Дальше делай так с каждым новым тестом, это пять секунд.

9. Заведи `tests/resetDb.ts` — функцию, которая выполняет `schema.sql` и `seed.sql` через пул (образец в лекции, раздел «Известное состояние: база перед каждым тестом»).
10. Напиши `tests/cards.test.ts`: `beforeEach(resetDb)`, `afterAll` с `pool.end()` и один тест — `GET /cards` отвечает `200` и отдаёт три карточки. Прогони.
11. **Проверь предохранитель.** В `.env.test` временно замени `kanban_test` на `kanban`, прогони `npm test` — прогон должен остановиться с твоим сообщением, **не выполнив ни одного теста**. Верни файл как было и убедись, что карточки в рабочей базе на месте:

```bash
psql -d kanban -c "SELECT title FROM cards;"
```

**Готово, когда:**

- [ ] `npm test` выполняется одной командой из папки `server/` и завершается сам, не зависая;
- [ ] в отчёте три зелёных теста: два на токен, один на `GET /cards`;
- [ ] `.env.test` есть на диске и **отсутствует** в коммитах — проверь панель Source Control;
- [ ] `app.ts` экспортирует приложение, `app.listen` остался только в `index.ts`, `npm run dev` работает как раньше;
- [ ] вывод тестов не забит строчками логгера;
- [ ] намеренно сломанный тест краснеет, и по отчёту понятно, что именно разошлось;
- [ ] прогон с рабочей базой в `.env.test` останавливается предохранителем, и карточки в `kanban` целы;
- [ ] в ветке отдельные коммиты: обвязка и тестовая база, разделение `app.ts`/`index.ts`, юнит-тест, первый тест ручки.

> [!TIP] Совет
> Три ошибки, на которые уходит больше всего времени, и как они выглядят:
>
> - **тесты прошли, а команда висит в терминале** — забыт `pool.end()` в `afterAll`: соединения открыты, и Node считает, что работа не закончена;
> - **ошибка подключения к базе, где в адресе `undefined`** — переменные окружения не успели загрузиться: загрузка `.env.test` должна быть в файле из `setupFiles`, а не где-то в тесте;
> - **`Cannot find module`** — в импорте забыто расширение `.ts`. Правило темы 4 действует и в тестах.

## Задание 3 (оценочное). Тикет KAN-7

Задача целиком по конвейеру: разведка, постановка (`proposal.md` и спека), `design.md` и `tasks.md`, реализация по шагам, архивация.

Влей `feature/vitest-setup` в `main` своей копии и создай ветку `feature/api-tests`.

> **KAN-7: Правила доступа держатся на честном слове**
>
> В теме 6 доска научилась отличать своих от чужих: чтение открыто всем, изменения — только вошедшим, чужую карточку удаляет модератор и никто больше. Проверено это было один раз, руками, в день сдачи.
>
> С тех пор код меняется каждую неделю, а правила никто не перепроверяет. Причём поломка этих правил — из тех, что не проявляются ничем: убери `requireAuth` с одного роута, и сервер продолжит работать, доска — открываться, ошибок не будет нигде. Просто удалять чужие карточки сможет любой.
>
> Нужен способ проверять все правила разом, одной командой, за секунду.
>
> **Критерии приёмки:**
>
> 1. `npm test` из папки `server/` прогоняет все тесты и завершается сам; тесты работают только с базой `kanban_test`, данные в рабочей базе после прогона не тронуты;
> 2. Чтение доски: `GET /cards` без входа отвечает `200` и отдаёт карточки;
> 3. Создание: без cookie — `401`; после входа — `201`, и в ответе та карточка, которую просили;
> 4. Удаление разобрано по всем ветвям: своя — `204`, чужая — `403` (и карточка остаётся в базе), чужая из-под модератора — `204`, несуществующая — `404`, негодный `id` в адресе — `400`;
> 5. Владелец новой карточки берётся из токена — это проверено **поведением снаружи**, без заглядывания в базу;
> 6. Отдельным файлом — тест сценария: регистрация → попытка создать карточку до входа (`401`) → вход → создание (`201`) → карточка видна на доске → чужую удалить нельзя → свою можно → выход → создание снова `401`;
> 7. Тесты независимы: перестановка тестов местами и повторный прогон ничего не меняют, оба файла проходят и вместе, и по отдельности;
> 8. Ни один тест не проходит «сам по себе»: если убрать `requireAuth` с `POST /cards`, прогон краснеет.

Образцы — лекция, разделы «Первый тест ручки», «Вход внутри теста», «Весь семинар темы 6 — одним файлом» и «Из ручек — сценарий». Изменение назови `api-tests` — заводит его агент скиллом `openspec-new-change`.

> [!NOTE]
> Изменение в этот раз необычное: оно не добавляет приложению ни одной новой возможности, а записывает уже существующие. В спеке появятся требования, которые до сих пор жили только в коде и в голове — «чужую карточку удалить нельзя», «несуществующая отвечает `404`». Это нормальная и очень частая в работе ситуация: поведение есть, а зафиксировано нигде. Заодно увидишь, насколько критерии приёмки и список тестов — одно и то же: пункты выше переписываются в `it(...)` почти дословно.

Три подсказки по местам, где обычно застревают.

**Критерий 5.** Владельца карточки `GET /cards` не отдаёт — значит, в лоб не проверить. Проверяется косвенно, поведением: зарегистрируй в тесте нового человека, создай карточку от его имени, войди Анной и попробуй удалить эту карточку. `403` доказывает, что владельцем записан не тот, кто вошёл сейчас, а тот, кто создавал. Если бы `owner_id` брался из константы или из тела запроса — пришёл бы `204`.

**Критерий 7.** Проверяется буквально: поменяй два `it` местами и прогони; потом прогони каждый файл отдельно (`npm test tests/cards.test.ts`), а потом оба вместе. Если вместе падает, а по отдельности нет — файлы дерутся за базу, лечится строчкой в конфигурации из лекции.

**Критерий 8.** Убери `requireAuth` из строки `POST /cards` в файле роутов, прогони `npm test`, посмотри на список красного и **верни `requireAuth` обратно**. В описании merge request напиши, какие тесты покраснели. Это и есть доказательство, что твои тесты не декоративные.

Покраснеет при этом больше одного теста, и это правильно. Очевидный — «без входа отвечает `401`»: раз проверки нет, приходит `201`. А следом упадёт и тест на успешное создание, причём с `500`: контроллер зовёт `currentUser(req)`, а тот при отсутствии `requireAuth` намеренно бросает исключение — та самая «громкая ошибка» из темы 6. Третьим упадёт сценарий, у которого этот шаг внутри.

> [!WARNING] Предостережение
> Если после снятия `requireAuth` прогон остался зелёным — тесты бесполезны, и задание не зачитывается. Смотри в первую очередь на `await`: забытый `await` перед `request(app)` делает тест вечнозелёным, а выглядит он при этом совершенно нормально.

**Готово, когда:**

- [ ] `npm test` показывает зелёный прогон, тестов не меньше десяти;
- [ ] все восемь критериев приёмки закрыты тестами, и по названиям `it` видно, какой пункт где;
- [ ] сценарий лежит отдельным файлом и читается сверху вниз как рассказ;
- [ ] названия тестов говорят, что именно проверяется, — «работает правильно» не считается;
- [ ] снятый `requireAuth` красит прогон, и в описании MR перечислено, какие тесты упали;
- [ ] после прогона `psql -d kanban -c "SELECT title FROM cards;"` показывает твои рабочие карточки нетронутыми;
- [ ] в `openspec/changes/archive/<дата>-api-tests/` лежат все пять файлов: `proposal.md`, спека, `design.md`, `tasks.md`, `report.md`;
- [ ] история коммитов читается как постановка → решение → шаги реализации → архивация;
- [ ] ветка отправлена в твою копию, открыт merge request с описанием: что сделано и как проверить.

**Сдача:** merge request из `feature/api-tests` в `main` твоей копии — **не вливай его сам**, его проверяет преподаватель. Приёмка — по зачётной системе курса: все критерии выполнены → зачтено, иначе замечания в MR и доработка до дедлайна (подробнее — в [«Организации работы»](../COURSE-SETUP.md)).

> [!TIP] Совет
> Тесты — та часть работы, где агент полезнее всего: материал шаблонный, а критерии приёмки у тебя уже расписаны. Но проверяй за ним по списку из лекции (врезка «тесты и агент»), и особенно два пункта: есть ли в каждом `it` хоть один `expect` и стоит ли `await` перед каждым запросом. И помни главное правило: **красный тест не чинят правкой ожидания**. Если агент предлагает поменять `403` на `200`, чтобы «прошло», — он удаляет проверку, а не исправляет ошибку.

## Частые ошибки — проверь себя перед сдачей

- В Insomnia адрес написан с `/api` — прокси Vite к ней отношения не имеет, правильный адрес `http://localhost:3001/cards`;
- Тело запроса в Insomnia задано как Plain Text вместо JSON — сервер отвечает `400` на совершенно правильный запрос;
- `.env.test` закоммичен вместе с паролем — из истории Git его уже не вычистить;
- Предохранитель в `tests/setup.ts` не написан — однажды прогон сотрёт рабочую базу, и предупреждения не будет;
- Забыт `await` перед `request(app)` — тест зелёный **всегда**, в том числе на сломанном эндпоинте; главная ошибка темы;
- В `it` нет ни одного `expect` — запрос отправлен, ответ никто не проверил;
- Тест ни разу не краснел — значит, неизвестно, проверяет ли он хоть что-нибудь;
- Забыт `pool.end()` в `afterAll` — тесты прошли, команда висит в терминале;
- `beforeAll` вместо `beforeEach` — тесты по одному проходят, вместе падают;
- Два файла тестов дерутся за базу — прогон падает через раз и каждый раз по-разному; лечится `fileParallelism: false`;
